# 이슈 #9 — 80문항 개편 검증

## 2026-11-10 재개 검증

- Chrome 자동화는 여전히 `stagingStatus` HTTP401. 정상 WebKit 브라우저는 실제 Staging Auth/App Check를 통과했고 80문항·사전 동의·완료 확인·서버 모의 PDF·문제집별 상세 응답 저장까지 성공했다. 아래 11월9일의 전체 흐름 미검증 상태 중 WebKit 항목을 해소한다. 실제 Safari 기기 성공으로 해석하지 않는다.
- 별도 실제 WebKit 시험에서 모의 fail-once의503 → 같은 요청 재시도200 → 동일 요청 중복200/duplicate=true를 확인했다. 기존 PDF 객체 generation 불변, 원본 PDF 하이픈 전화번호·A4 1페이지·비교 차트·체질별 실제 집계(각5점)를 확인했다. 실제 이메일은 보내지 않았다.
- Staging의 기존 Drive 및 Gmail 인증 갱신이 실패해 소유자의 재인증이 필요하다. 운영 인증을 복사하지 않는다. Drive 재인증 화면을 다시 열었으며 소유자 승인 대기다. 실제 마스터 Google 로그인·문제집 ON/OFF·상세 응답 검수도 사용자 확인을 요청했다.
- Staging 메일 수신자는 아직 이전 네이버 설정이며 현재 한의원 Gmail과 다르다. `gmail-sender.ts`의 테스트 수신자 검사에 Gmail을 추가하되 Naver/Gmail 이외 주소·헤더 삽입과1시간 초과 발송 창은 계속 거부한다. 브라우저 임의 수신자 입력을 허용하지 않는다.
- 수정 후 UI86+정책9+서버84=179개 테스트 및 운영·Staging·Functions 빌드 성공. 수신자 Secret·발송 창은 변경하지 않았고 실제 발송은0건이다. 실제 시험1건을 진행하려면 고정 수신자 변경·Gmail 소유자 재인증·제한된 발송 창에 대한 구체적인 확인이 필요하다.
- 운영 배포/main 병합/태그 생성은 진행하지 않는다. 실제 Drive 업로드, 실제 메일 수신, 사용자 관리자 검수는 아직 완료가 아니다.

## 적용 범위

개발 브랜치 `develop/questionnaire-80`, Staging `yingyangtest` 전용 검증이다. 운영 main·Functions·Hosting·발송 설정과 출시 태그는 변경하지 않는다. 이슈의 운영 배포 전 보고 조건에 따라 운영 반영은 후속 단계다.

## 구현

- 전화번호는 입력 시 숫자/하이픈을 인식하고 확인 화면과 신규 생성 PDF에서는 `010-0000-0000` 형식으로 표시한다. 내부 전송은 기존 숫자만 유지한다. 10자리 기존 번호는 자릿수를 보존해 표시하며 없는 숫자를 채우지 않는다. 이미 발송/보관한 PDF는 재작성하지 않는다.
- 전화번호 후속 수정 검증: UI86+정책9+서버83=178개 통과. 숫자/하이픈 입력의 동일한 전송 값과 입력란 blur 표시, 신·구 PDF 한글/전화번호·페이지 경계를 확인했다. 운영/Staging/Functions 빌드 통과. 기존 App Check·Drive 실제 환경 미검증 항목은 그대로 남는다.
- 현재문항 `sasang-80`, 응답 version 2: 선천적 사상체질/후천적 사상페르소나 각 40문항. 내부 체질 그룹 8개×10문항. O=1, X=0. 체질별 0~10점, 최고점 동점은 모두 표시하고 확정 진단은 하지 않는다.
- 이슈 #9 본문에서 80문항을 기계적으로 추출해 `src/sasang-source.json`에 등록했다. 중복 공백·문장 끝 공백·표기 오류로 보이는 원문도 수정하지 않았다. SHA256 `34720d7efe18584c60f8cc796a0e47a18a2701d00c867e984478f2daeda48294`.
- 사용자 화면은 문항 원문과 O/X만 표시한다. 체질 그룹 이름은 관리자 상세에만 표시한다.
- 기존 `src/questions.ts`는 변경하지 않았다. 기존 50문항은 `legacy-50`, version 1, 기존 `yingyang:acquired/innate` 키를 유지한다. 새 문항은 `yingyang:sasang-80:acquired/innate`와 별도 완료 증명을 사용한다. 기존 자료를 새로운 길이/점수 규칙으로 이전하지 않는다.
- 관리자 문제집 관리에서 문제집 단위로 활성화한다. 기본은 새 문항 ON/문항 1.0 OFF. 하나 이상 ON이어야 한다. 문항 1.0 OFF일 때 탭과 현재문항이라는 별도 제목이 없다. 문항 1.0 ON일 때만 두 탭을 표시한다. 마스터의 최근 Google 재인증과 세대 조건부 저장을 요구한다. 일반 관리자·미인증·오래된 인증은 설정을 변경할 수 없다.
- 비활성 문제집의 신규 완료/발송은 서버에서도 차단하지만 기존 기록 조회·PDF에는 활성 설정을 적용하지 않는다. 운영 전환 때 미완료 기존 사용자 지원 기간 및 문항 1.0 활성화 여부를 결정해야 한다.
- 신규 결과 PDF: 가로 점수표 2개, 청록 선천적/주황 후천적 개별 차트 2개, 합산 없는 중첩 비교 1개. 위 태양/오른쪽 태음/아래 소양/왼쪽 소음, 공통 0~10점. 한글 A4 1페이지. 기존 50문항 PDF 레이아웃 경로는 그대로 유지한다.
- 기존 이메일·Drive 업로더·파일명·중복 방지·7일 PDF 다운로드와 무기한 Drive 정책을 재사용한다. 새 문제집의 완료 증명과 전송 표식에 버전을 결합하고 기존 문제집의 중복 표식은 유지한다.

## 상세 응답과 개인정보

- 관리자 상세 조회를 위해 신규 접수부터 문제집 버전·원 응답·집계를 기존 비공개 PDF 저장소의 `details/{id}.json`에 7일 임시 보관한다. 새 DB·버킷·서비스·유료 리소스를 만들지 않는다. 이름/전화번호를 상세 JSON에 중복 저장하지 않는다.
- 상세 응답은 Auth/App Check와 서버 관리자 권한 확인 후에만 반환한다. 조회 감사 표식은 기존 비공개 감사 경로에 남기고 응답/점수/이름/번호를 일반 앱 로그에 출력하지 않는다. 상세 응답은 Drive 백업 대상이 아니다.
- 생성 후 7일이 지나면 상세 조회를 즉시 거부하고 기존 버킷 7일 삭제 정책이 적용된다. 재시도는 기한을 늘리지 않는다. 브라우저도 기존 검사별 마지막 저장 후 7일 만료·전체 삭제 규칙을 유지한다.
- 신규 상세 보관을 반영한 동의 고지와 방침을 작성했다. Staging 동의 버전 6, 향후 운영용 새 동의 버전을 분리했다. 재동의는 기존 응답을 재채점하거나 삭제하지 않는다. 운영 고지 적용은 운영 배포 전 확인 대상이다.

## 이전 기록 호환성

- 운영 저장소를 읽기 전용 점검한 시점에 남아 있는 발송 이력은 0건이었다. 실제 과거 응답을 확보하거나 복원했다고 보고하지 않는다. 기존 7일 수명 정책과 Drive/메일 사본은 변경하지 않는다.
- 이전 배포 소스의 저장 스키마와 기존 형식 테스트 자료를 대조했다. 문제집 식별자가 없던 이전 형식은 UI에 `문항 1.0 · 이전 기록`으로 표시한다. 원본 기록을 덮어쓰거나 새 문제집 점수로 다시 계산하지 않는다.
- 이전 버전은 서버 원 응답을 보관하지 않았으므로 과거 원 응답을 추정하지 않는다. 상세 JSON이 없는 기록에는 기존 PDF 확인 안내를 표시한다. 앞으로 접수한 기존 50문항도 원래 채점으로 상세를 보관한다.

## 검증

- 자동 테스트: UI 82, 배포/공개 정책 9, 서버 83(총 174) 통과. PDF 간격·축 이름 위치 수정 후 서버 검증 및 실제 렌더링을 다시 실행해 통과했다. 운영·Staging·Functions 빌드 모두 성공했다.
- 로컬 Chrome/WebKit에서 각각 80문항을 원문과 대조하며 끝까지 진행. 미응답 다음 차단, 이전 이동·수정, 새로고침 이어하기, 검진별 독립 재검진, 기존 저장 키 보존 확인.
- 320/390/768/820/1024/1440px×소/중/대×Chrome/WebKit = 36조합에서 차트 3개와 가로 넘침 없음 확인. 실제 iPad·Safari 기기 검증을 의미하지 않는다.
- 서버 O/X 범위·문항 수·혼합 버전·수신자 삽입 거부, 공동 최고점/0점/10점, 문제집별 완료 증명과 KST, 관리자 권한·상세 만료, 문제집 비활성화·CAS·최근 재인증 테스트.
- 실제 새 PDF를 렌더링해 한글/숫자/축/범례/잘림/겹침을 육안 검수했다. PDF 파서로 A4 1페이지와 모든 텍스트의 페이지 경계를 확인했다. 새 PDF의 이메일 MIME·Drive 업로드/중복 경로는 모의 어댑터로 검증하며 실제 메일은 발송하지 않는다.
- 기존 Staging Drive OAuth 갱신은 authorization 오류. 사용자가 현재 확인할 수 없어 재인증을 건너뛰라고 지시했다. 실제 새 PDF의 Drive 업로드 및 해당 계정 확인은 미완료다. 운영 인증을 복사하거나 App Check를 우회하지 않는다.

## Staging 및 후속 상태

- 구현 커밋 `073ed5b`를 GitHub 개발 브랜치에 푸시했다. Staging Hosting·Functions 9개 배포 성공 및 모든 함수 ACTIVE 확인.
- `https://yingyangtest.web.app` HTTP200, 로컬 빌드 자산 일치, noindex/nofollow/noarchive 확인. 기본 문제집은 현재문항 ON/문항 1.0 OFF다.
- `/previews/issue-9-pdf.png`, `/previews/issue-9-admin.png`, `/previews/issue-9-mobile.png` 모두 HTTP200과 PNG 원문 확인. 로그인 없이 읽을 수 있는 가상 데이터 미리보기다. 관리자 이미지는 로컬 가상 검증 화면이며 실제 관리자 로그인 성공의 증거가 아니다.
- 실제 Staging 자동 브라우저에서 계정 로그인 후 환경 확인 `stagingStatus`가 App Check HTTP401로 거부되어 검진 진입 전에 중단했다. 이 시험으로 80문항 서버 처리 성공을 주장하지 않는다. App Check 우회·비활성화는 하지 않았다. 일반 사용자 브라우저에서의 Staging 전체 흐름 및 실제 마스터 Google 로그인·문제집 설정 저장 검수는 남아 있다.
- 실제 메일 0건, 실제 Drive 업로드 0건. 메일 MIME와 새 PDF/Drive 업로드 모의 어댑터 테스트는 실제 수신·원격 업로드 확인과 다르다. Drive 재인증과 실제 업로드는 사용자가 보류했다.
- 운영 Hosting 릴리스가 작업 전 기준과 일치하고 운영 Functions에 이번 작업 이후 갱신이 없음을 확인했다. main은 `f05a837` 유지, 출시 태그 생성 없음.
- 이슈 #9는 열린 상태로 둔다. 남은 실제 환경 검증과 운영 배포 전 확인을 마친 뒤 운영 적용 여부를 결정한다.
