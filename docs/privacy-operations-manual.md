## 2. 메일·파일 삭제 절차 (수동·대상 한정)

1. 실제 처리자와 계정/기기 소유자가 삭제 범위·기간·법정 보존/분쟁 예외를 확인한다. 미확정이면 담당자에게 이관하고 임의로 지우지 않는다. 실제 환자 자료를 이 검토에 가져오지 않는다.
2. 날짜/개별 메일 식별 정보·정해진 제목 등으로 **대상 메일만** 찾고 발신·수신·첨부가 승인된 대상인지 확인한다. 메일함 전체 삭제나 무관한 파일 일괄 삭제는 하지 않는다.
3. Gmail 소유자는 보낸함·전체보관함/라벨·전달 사본을 확인하고 대상 메시지를 삭제한 뒤 대상 휴지통에서도 영구 삭제한다. 네이버 담당자는 수신함/첨부·휴지통·전달/공유·POP/IMAP 클라이언트를 함께 확인한다. 보관처리/라벨 이동을 삭제로 집계하지 않는다.
4. 다운로드/뷰어 임시 폴더·동기화 사본·기기 휴지통·출력물·백업 목록을 확인한다. 사본별 책임자가 자신의 권한 범위에서 삭제·파쇄하고, 공급자/기기 백업의 실제 잔존기간은 별도 기록한다. 앱 버튼으로 이 사본들이 없어졌다고 판단하지 않는다.
5. 담당자와 검토자가 날짜·대상 범위·결과·미삭제 예외/다음 확인일을 기록한다. 삭제 확인을 위해 이름·번호·PDF·건강 응답 원문을 이슈/로그/새 관리 파일에 재복사하지 않는다.

Gmail의 휴지통 이동과 영구 삭제는 다르다. [공식 삭제 안내](https://support.google.com/mail/answer/7401?hl=ko). 네이버/클라이언트의 실제 정책과 동기화 결과는 계정 담당자가 확인한다. 이번 문서 작성으로 어떤 메일 삭제도 실행하지 않았다.

## 3. 브라우저 자료·권리 요청 대응

- 이용자에게 ‘검사 데이터 모두 삭제’는 로컬 검사/폼·증명을 지우며 글자 크기는 유지할 수 있다고 안내한다. 다른 탭도 동의 화면으로 돌아가는지 확인한다. 계정 로그아웃과 자료 삭제를 구분한다.
- 메일 전송 후 삭제/철회 요청은 [실제 처리자·한의원 창구: 확인 필요]로 이관한다. 본인 확인에 과도한 정보/원 PDF를 다시 요구하지 않는다. 이미 전달된 사본의 취소/원격 삭제를 약속하지 않는다.
- 진료기록/법정 보존/잠긴 감사기록 등의 예외는 담당자가 근거와 범위·기간·접근 제한을 알려 처리한다. 서버 저장 안 함을 이유로 메일함/기기 사본을 무시하지 않는다.
- 현재 사전 동의 증명의 만료 키·계정별 요청 취소·장기 증빙 부족은 정책 결정 후 필요한 코드안을 보고한다. **이번에는 문서만 작성하고 기능을 추가하지 않았다.**

| Gmail API 접수 성공 | API 접수만 기록. 실제 수신은 계정 담당자 확인과 구분 | API200만으로 한의원 도착 확정 |
| 동일 티켓 sent/unknown | sent는 중복 완료, unknown/sending은 차단 상태 유지 | 다른 티켓으로 우회 재발송 |
| KST50회 도달/공유 저장 실패 | 서버 차단을 유지하고 담당자에게 상황 안내 | 한도 상향/제어 창 개방·데이터 변경을 임의 수행 |
| OAuth 만료/철회/계정 변경 | 발송 중지 확인 후 계정 소유자에게 재인증·검증/운영 전략 승인 요청 | 비밀번호/토큰을 채팅에 받거나 임의 권한 확대 |

일반 Gmail External Testing 토큰은 공식 문서상 보통7일 만료 조건이 있다. 실제 토큰 상태·남은 유효시간을 이번에 시험한 것은 아니다. Production 게시가 영구 토큰/검증 면제를 뜻하지 않는다. 소유자·대체 담당, 민감 권한 검증/예외, 연락·중지·재인증 시간을 운영 전에 확정한다. [Google 토큰 수명](https://developers.google.com/identity/protocols/oauth2#expiration).

현재는 실발송 창을 계속 닫는다. 장애 대응/재인증을 위한 메일 발송도 별도 승인 전 하지 않는다. UI 모의 성공을 실메일 성공으로 바꾸지 않는다.

## 5. 정기/변경 시 점검표 — 계획만

| 시점 | 담당/점검 | 완료 판정 | 현재 상태 |
| --- | --- | --- | --- |
| 업무 사용 전 | 한의원: 수신 업무 동의·계정 소유/최소 접근·권리 문의처 | 명칭·책임·계정 역할 서면 확인 | [확인 필요] |
| 정책/배포 승인 전 | 실제 처리자: 법적 관계·공급자/국외 처리·증빙·기간·진료기록/연령 범위 | 최종 전문·전문 버전·시행일·동의/게시 범위 승인 | 미완료 |
| 승인된 운영 발송 전 | 기술 담당: 고정 수신자·환경 분리·Auth/App Check·50회·중복·토큰 전략 | 설정 검증·장애/중지 수순·담당자 | 현재 설정 유지, 운영 승인은 없음 |
| 정기 | 각 사본 담당: 보유기한·휴지통·전달/백업·삭제 확인 | 개인 원문 없는 확인 기록/예외 목록 | 실제 정리 미확인 |
| 역할/계정/비밀 교체 시 | 관리자: 최소 IAM·사용 버전·배포 리비전·롤백 의존 | 승인된 회수/비활성/폐기·재인증 결과 | 이번 변경 안 함 |
| 보안 점검 시 | 로그 관리자: 범위 한정 PII 패턴/권한/내보내기/sink/백업 | 범위와 누락 여부 명시, 원문 외부 반출 없음 | 과거 결과만 참고 |
| 비용/장애 점검 시 | 운영자: 실제 청구·월1만원 알림 수신·인스턴스/작업량 | 알림 수신/담당·중지 계획·승인된 롤백 | 실청구/수신 미확인. 알림/50회는 요금 상한 아님 |

`_Default`와 잠긴 `_Required`를 같은 기간으로 취급하지 않는다. GCS lifecycle은 비동기이며 제어 객체가 없어지면 기본 발송 차단이다. Secret 비활성화는 파기가 아니고, 구버전 폐기는 롤백 가능성에 영향을 준다. 어떤 설정도 이번 문서 작업에서 변경하지 않았다.

공식 근거: [Cloud Logging 보관](https://docs.cloud.google.com/logging/docs/store-log-entries), [GCS lifecycle](https://docs.cloud.google.com/storage/docs/lifecycle). 실제 계정 백업/메일 규칙·운영 프로젝트 설정은 별도 확인/승인 대상이다.
