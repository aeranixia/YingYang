# E단계 실행 기록

2026-10-27. 사용자에게 가상 데이터 E 시험 전체 승인을 받았다. 대상은 `yingyangtest` / `develop/v1.2`다. 지정 개인 Gmail에서 지정 개인 네이버로만 시험하며 실제 주소·OAuth 클라이언트 비밀·토큰은 이 저장소/이슈에 기록하지 않는다. 한의원 주소 적용과 운영 변경은 별도 승인 대상이다.

## 구성

- Gmail API 활성화, External/Testing 데스크톱 OAuth 클라이언트는 계정 소유자가 생성했다. 로컬 loopback HTTP 콜백, 무작위 state, PKCE S256, `gmail.send` 단일 권한으로 소유자가 브라우저에서 동의했다. 토큰은 출력/파일 저장 없이 Secret Manager로 전달했다.
- `STAGING_GMAIL_CLIENT`, `STAGING_GMAIL_REFRESH_TOKEN` 두 비밀을 추가했다. 첫 비밀은 클라이언트 정보·고정 발신/테스트 수신자·시험 허용 종료 시각을 포함한다. 한의원/운영 수신자나 환경 간 fallback은 없다.
- 최대 1시간 이내의 서버 허용 창에서만 실제 발송이 가능하며 시험 후 다시 끈다. Secret과 GCS 제어 객체를 매 요청 읽는다. 현재 창의 기준은 아래 실제 결과에 기록한 GCS 제어 시각이며, 이미 전송 중인 요청까지 철회한다는 보장은 아니다.
- 전용 키 없는 실행 계정 `yingyang-staging-mail-runtime`을 생성했다. 빌드 기본 계정과 분리하고 개별 서버 키/두 Gmail 비밀의 Secret Accessor 및 아래 버킷의 Object User만 부여했다. 서비스 계정 키 파일은 없다.
- 비공개 Standard 버킷 `yingyangtest-mail-state-495270334718`, 서울 리전, uniform access·public access prevention, 버전 관리/soft delete 끔, 생성 후 2일 기준 비동기 lifecycle 삭제. 기존 배포 버킷을 재사용하지 않는다.

## 경로와 제한

기존 사용자 화면과 `submitMockReport`는 모의 처리로 유지한다. 실제 시험은 별도의 관리자 테스트 callable `prepareStagingReport` / `submitStagingReport`로 분리했다. 따라서 기존 모의 화면의 ‘실제 발송 없음’ 안내가 실제 발송 동의로 재사용되지 않는다. 실제 테스트는 소유자 승인을 받은 운영자만 수행한다. 일반 이용자 실제 발송 화면/운영 동의 문구는 후속 검토 대상이다.

- Auth `stagingTester`와 추가 `stagingMailTester` 권한, 실제 App Check, 테스트 프로젝트·본문 크기·가상 인적사항·응답·별도 `staging-e-draft-1` 동의를 검증한다.
- 서버가 서명한 15분 티켓을 발급하고 UID/입력/고정 발신·수신 설정에 결합한다. 클라이언트는 수신자를 지정하지 못한다. 만료 티켓은 GCS 표식이 삭제되더라도 재사용하지 못한다.
- GCS 세대 번호 조건부 쓰기로 처리 예약·상태 갱신, 한국 날짜 기준 전체 하루 최대 10번 발송 시도 카운터를 구현했다. 전송 전 실패라도 보수적으로 시도 수가 소진될 수 있다. 저장소를 읽거나 예약할 수 없으면 발송하지 않는다.
- 객체에는 불투명 요청 키/HMAC/상태/시도/시각/논리 만료 및 일일 횟수만 저장한다. 이름·전화번호·응답·점수·PDF·이메일 주소·Gmail 원문은 저장하지 않는다. 메타데이터를 완전한 익명정보라고 단정하지 않는다.
- 상태는 preparing/failed/sending/sent/unknown으로 구분한다. 발송 전 명확한 실패만 최대 3회 준비 재시도, 완료 중복은 재발송 없이 완료 반환. sending/unknown이나 Gmail 응답·상태 기록 불명은 자동 재발송하지 않는다.
- 메타데이터 논리 만료 24시간과 실제 비동기 삭제를 구분한다. 티켓은 더 짧은 15분이다. 정확한 24시간 물리 삭제, 다른 티켓/새 검진에 대한 업무상 중복, Gmail과 GCS의 정확히 한 번 트랜잭션을 보장하지 않는다.
- 함수 각각 최소 0/최대 1, 동시성 1, 512MiB/CPU1/30초다. 네 callable의 합계 인스턴스 상한이 1은 아니다. OAuth 갱신 5초·Gmail 요청 10초 제한이며 발신 HTTP를 자동 재시도하지 않는다.

실제 시험 PDF는 A4·한글·원형 숫자·서버 재집계·이름_끝4자리.pdf를 유지하고, 기존 모의 PDF의 ‘실제 이메일 미발송’ 문구를 ‘실제 이메일 테스트’로 바꿨다. PDF/MIME는 메모리에서만 만들고 처리 후 Buffer를 정리한다. 제목·본문에는 인적사항을 넣지 않으며 수신 메일함 첨부 보관은 별도다.

## 검증 상태

실제 발송 전 자동 테스트 64개(UI/엔진 37 + 배포 보호 2 + 서버 25), 운영 및 서버 빌드 성공, Functions 전체 audit 0개를 확인했다. 기존 54개를 유지했다. 새 시험은 서명/만료/입력·수신 결합, 공유 중복/인스턴스 재생성, 동시 예약, 인증 실패 후 재시도, 결과 불명 및 Gmail 성공 후 상태 기록 실패, 일일 10건/손상 카운터 차단, 고정 MIME·한글 파일명, 실제 시험 PDF/동의 분리를 검증한다.

실제 GCS에서 읽은 세대 번호와 조건부 신규 생성 충돌 412를 확인했다.

### 1차 실제 발송 결과 (2026-10-27)

- 커밋 `be6d3b0`, `8827bf6`을 Staging에 배포했다. 64개 테스트와 빌드가 통과했다.
- Gmail API가 가상 PDF 1건을 HTTP 200 / `gmail-accepted`로 접수했다. 사용자가 네이버 수신 및 PDF 내용 모두 정상임을 확인했다. 확인 항목은 한글·날짜·가상 전화번호·파일명 `가상테스터_1234.pdf`, 후천적 3/3/2/2 합계 10, 타고난 22/20/20/18 합계 80이다.
- 같은 티켓 재요청은 HTTP 200 / `duplicate: true`로 반환했고 추가 발송하지 않았다. 브라우저의 수신자 필드 주입은 HTTP 400 / `INVALID_ARGUMENT`로 거부했다.
- 공유 저장소의 최종 상태는 `sent`, 당일 발송 시도는 1건이다. 발송 창은 종료했다. 준비 단계 차단 중에는 실제 메일을 보내지 않았다.
- 현재 발송 창의 기준은 GCS `v1/control/mail`의 `until`이다. 세대 번호 조건부 갱신을 사용하고, 객체 누락·만료·조회 실패 시 발송을 차단한다. Secret의 과거 허용 시각 대신 이 값을 사용한다. 최초 닫힌 창 요청은 `window-validation` 단계에서 차단됨을 확인했다. 이미 진행 중인 요청의 취소까지 보장하지 않는다.
- 배포 사이트에서 실제 Auth/App Check를 통한 기존 PDF 모의 처리가 정상임을 확인했다. Staging HTTP 200 및 빌드 HTML 일치, 운영 HTTP 200 및 기존 HTML 해시 일치를 확인했다. 운영 배포·main 병합·태그 생성은 하지 않았다.
- 이번 시험은 Chrome 자동화와 사용자 수신 확인이다. 실제 기기/Safari, 실제 OAuth 철회·재동의, 실제 장애 중 강제 재시작 및 전달 지연은 이번 시험에서 검증하지 않았다. 실패/불명 상태·재시도·경합은 자동 테스트 결과와 구분한다.
- 한의원 수신자는 등록하지 않았다. 전환과 최종 수신 확인은 별도 승인 후 진행한다.

## 운영과 보관

운영 `yingyangcheck`·main·기존 태그는 유지하고 v1.2.0 태그를 만들지 않는다. 한의원 주소는 미등록이다. 실제 환자 자료는 사용하지 않는다.

Gmail API 성공은 수신함 도착과 다르다. 네이버 수신함/스팸함과 PDF 내용·파일명은 계정 소유자가 확인해야 한다. 가상 테스트 메일/다운로드는 검증 후, 최대 7일 내 양쪽 메일함·휴지통과 함께 수동 정리한다. `gmail.send`로 읽기/삭제 권한은 요청하지 않았다.

기존 월 1만원 예산 알림은 과금 차단이 아니다. 추가 Secret 버전·GCS 작업/저장·빌드·실행의 종량제 비용이 생길 수 있으며 실제 비용 0원을 보장하지 않는다. Redis/Firestore·별도 상시 서버·추가 Scheduler는 생성하지 않았다. OAuth Testing refresh token의 일반적 7일 만료와 재승인이 필요할 수 있다. 상세 원칙은 [E 사전 계획](staging-e-preparation.md)을 따른다.
