# Chrome 자동화 App Check403 — 안전한 진단 계획

후속 사용자 승인에 따른2026-10-31 읽기 전용 조사/최소 재현은 [원인 조사 결과](app-check-chrome-investigation.md)에 기록했다. 아래의 ‘미실행’은 최초 계획 작성 당시의 상태이며, 현재도 세부 원인 확정·수정 승인은 별도다.

2026-10-31. 이번 산출물은 진단 **계획**이다. 추가 요청 재현/클라우드 변경은 실행하지 않았다. 기존 이슈 #4 안에서 추적하며 새 이슈를 만들지 않는다.

## 확인된 사실과 미확인 사항

| 구분 | 사실/상태 |
| --- | --- |
| 사용자 일반 Chrome | [사용자 관찰 댓글](https://github.com/aeranixia/YingYang/issues/4#issuecomment-6543654508)에서 환경 확인 및 모의 흐름 모두 정상으로 보인다고 보고. 관찰 근거이며 모든 기기/버전의 보증 아님 |
| 개발자 Chrome 자동화 | 앞선 실제 점검에서 App Check 교환403/PERMISSION_DENIED(attestation 실패), SDK initial-throttle/throttled, callable401. 서버 auth VALID/app MISSING |
| WebKit 자동화 | 실제 reCAPTCHA/App Check·Auth 및 모의 흐름 통과. macOS/iOS Safari 실기기를 대신하지 않음 |
| 기존 설정 | 앞선 읽기 전용 조회에서 등록/허용 도메인 확인. 보안 임계값/디버그 토큰/강제 검증 설정 변경 없음 |
| 원인 | **미해결**. 자동화 신호·프로필/네트워크·확장·쿠키/저장소·발급/캐시·백오프·설정/SDK/공급자 오류 등 후보를 확정하지 않음 |

사용자 Chrome 정상 보고가 자동화403의 해소 증거는 아니고, 자동화403이 모든 사용자의 장애라는 증거도 아니다.

## 승인된 범위 안의 재현 절차 제안

1. `yingyangtest`와 현재 커밋·시각(KST/UTC)·정상 사용자 관찰 여부를 기록한다. 운영 접속/실환자/실메일을 사용하지 않는다. 검사 응답을 보내지 않는 환경 상태 요청부터 비교한다.
2. 평소 Chrome 프로필 수동 사용, 별도 QA 프로필의 수동 사용, 일반 Playwright Chrome 자동화, WebKit 자동화를 한 번에 한 변수씩 비교한다. 버전·OS·프로필 종류·확장 유무·네트워크 조건만 기록하고 정상 브라우저를 자동화처럼 보이게/반대로 위장하지 않는다.
3. 시도는 변형당 최대3회 제안. 오류의 Retry-After/SDK 백오프를 준수하고 반복401/403이면 중지한다. 저장소를 반복 삭제하거나 프로필을 무한 생성해 throttle을 피하지 않는다. 수동 성공/실패 확인은 사용자 동의 범위에서만 진행한다.
4. 상태는 구간별로 구분한다: reCAPTCHA 스크립트 로드 → App Check 교환 → 토큰 헤더 존재 여부 → Auth/App Check 서버 검증 → callable 응답. HTTP상태·공식 오류 코드·토큰 존재 참/거짓·검증 분류만 기록한다.
5. 토큰 원문·Authorization·비밀번호·전체 URL의 API키 쿼리·전체 HAR/trace·원 요청 응답 본문/건강정보는 출력하거나 이슈에 첨부하지 않는다. 스크린샷은 입력/계정 정보가 없는 검토용 화면으로 한정한다.
6. 필요하면 기존 권한으로 앱 등록·도메인·공급자·시계·SDK·키 유형/서비스 상태·권한/오류 메트릭을 읽기 전용 확인한다. 서비스 비밀/실제 이메일 값은 보고하지 않는다. 평가 호출 추가·메트릭/로그 유료 자원 생성이 필요하면 먼저 비용/범위를 보고한다.
7. 대조 결과가 쌓이기 전 원인을 단정하거나 로그인 코드를 재구현하지 않는다. 코드/의존성/배포 변경이 필요하면 재현 근거·수정안·회귀 검증·범위를 이슈 #4에서 제시하고 별도 승인받는다.

## 금지하는 해결 방식

- enforceAppCheck 또는 request.app/Auth/claim 검증 비활성화.
- 점수 임계값 하향, 허용 도메인 확대, 키 교체, 토큰 TTL 변경 등 임의 설정 완화.
- 디버그 토큰/CustomProvider를 무단 등록·공개하거나 기존 테스트 성공을 실제 reCAPTCHA 검증 성공으로 보고.
- 공급자의 보안 검증을 우회하는 stealth/지문 위장·타인의 세션/토큰 사용.
- 발송 창 개방·Gmail 호출로 정상 여부 판단, 실제 환자 데이터로 재현.
