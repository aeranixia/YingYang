## 2. 50회 제한의 정확한 의미

`functions/src/live-service.ts`의 공통 상수 `DAILY_MAIL_ATTEMPT_LIMIT=50`을 공유 카운터 비교에 사용한다. 인증된 `stagingStatus({})`는 같은 상수 `dailyMailAttemptLimit`를 반환하여 배포 후 확인에 사용한다. 일반 화면/환자 UX는 바꾸지 않는다. 모의 처리의 프로세스별 한도(기존 UTC 기준50회)는 실메일의 공유 KST 한도와 별개이며 변경하지 않았다.

| 규칙 | 동작 |
| --- | --- |
| 집계 단위 | 프로젝트의 고정 발신/수신 경로 전체, KST 날짜 `v1/days/YYYY-MM-DD`별 예약 수. 사용자별/성공건수별 아님 |
| 카운터 위치 | 기존 비공개 GCS. 읽은 generation의 조건부 쓰기만 허용. 경합 시 최대5회 재시도 후 차단. 과소 수용 가능, 초과 수용 금지 |
| 차감 시점 | 입력/티켓/중복 검증 → PDF 생성 → OAuth 준비 → **현재 시각으로 일일 예약** → sending 상태 기록 → Gmail 호출 |
| KST 경계 | 요청 시작 시각이 아닌 예약 시각 사용. PDF 준비 중 자정이 지나면 새 날짜에서 예약 |
| 실패 | 예약 전 입력/PDF/OAuth 실패는 미차감. 예약 후 전송 실패·결과 불명·sending 상태 기록 실패는 예약 유지. 자동 환급하지 않음 |
| 같은 티켓 | sent는 duplicate 성공 반환, 추가 차감/전송 없음. sending/unknown은 차단, 새 서비스 인스턴스에서도 재발송 금지 |
| 신규 티켓 | 별도 시도. 같은 내용을 새 티켓으로 반복하는 업무상 중복은 완전 차단하지 못함 |
| 51번째/손상 카운터 | resource-exhausted로 차단, Gmail 미호출. 읽기/쓰기 실패도 발송 전에 차단 |
| 제한의 한계 | 상태 쓰기/실행 중단으로 실제 Gmail 호출 없이 예약이 소모될 수 있음. 보수적 상한이며 정확한 성공/전달 건수 아님. 외부 부작용의 정확히 한 번 보장 아님 |

새 자동시험: 50개 성공 후51번째/손상값 거부, 49에서20개 동시 새 티켓 중1개만 통과, PDF 준비 중 KST 자정 경계, 실패 차감/중복 미차감/결과 불명 재전송 금지, 예약 전 실패0차감/예약 후 상태 오류 미환급. 모두 가짜 발신 함수이며 실제 이메일을 호출하지 않는다. 기존 티켓 중복·서비스 재생성·수신자 주입·Gmail 결과 불명 시험을 유지한다. 추가 발송량 증가 시 한도 숫자만 계속 올리지 않고 지연/큐/비용/오남용을 별도 재설계한다.

## 3. 개인정보 문제와 권장 흐름 — 승인 대기

[기존 실제 데이터 흐름 표/증거 구간](privacy-preproduction-review.md)을 기준으로 한다. 현재 응답·완료 증명은 브라우저에 무기한 남고, 완료 확인은 후기 동의 폼보다 먼저 50응답을 서버로 보낸다. 로그아웃은 검진 자료 삭제가 아니며 증명 저장용 signature에도 원 응답 사본이 있다.

**권장안 A:** 검사 시작 전 처리 안내 → 개인정보 수집/이용과 건강 관련 민감정보 별도 동의 → 검진 저장/이어하기 → 양쪽 완료 시 인증된 서버 완료 확인 → 이름/전화번호 입력·전송 요약·필요한 제공/국외 이전 동의 확인 → 전송. 사전 동의 버전/회차를 서버에서도 확인하도록 별도 개발한다. 현재 완료 확인 시각의 의미와 PDF 디자인을 유지할 수 있다.

- 장점: 첫 응답 저장·완료 확인 전송까지 사전 안내 가능, 완료 확인이 후기 폼 작성 시간 때문에 늦어지는 것을 피함.
- 단점: 검사 전 안내 부담, 역할/처리 국가/보관 정책이 먼저 확정되어야 함. 동의가 필요하지 않은 접속·보안 처리의 근거와 고지도 별도 정리.
- UX: 목적·항목·보관·삭제·거부 효과를 짧게 표시하고 상세 전문을 열어볼 수 있게 한다. 체크 미선택 기본, 일반·민감정보를 별도 선택. 독립 제공 동의는 실제 전송 시 다시 확인할 수 있게 하되 필요한 사전 민감정보 범위를 누락하지 않는다. 비필수 동의 거부로 진료 전체를 막지 않는다.
- 현재 구조의 사전 동의 증명 없는 보관 데이터는 검사 화면에 노출/자동 전송하기 전에 재안내와 선택을 받는다. 이름/번호는 여전히 후기 입력이고 클라이언트 영구 저장을 제안하지 않는다.

**대안 B:** 검진 중 서버 전송을 하지 않고 동의 후 완료 확인. 동의 전 브라우저 건강 응답 저장 문제는 별도 해결해야 하며 ‘서버 완료 확인 시각’이 늦어질 수 있다. 사전 화면을 줄일 수 있지만 시각·임시 저장의 처리 근거를 해결하지 못하므로 A를 우선 제안한다. 법적 필요성은 처리자/목적/근거 확정 후 책임자가 검토한다. 아직 둘 다 구현하지 않았다.

## 4. 7일 임시 저장·전체 삭제 상세 설계 — 승인 대기

### 저장과 만료

- 기존 `yingyang:acquired`, `yingyang:innate`의 v1 응답 구조·문항·집계를 보존하고, Staging 전용 저장 어댑터/메타데이터로 검사별 `savedAt`, 회차 ID, 정책 버전, expiry를 관리하는 안. 운영 키나 기존 검진 데이터는 이번에 변경하지 않는다.
- 마지막 **실제 응답/진행 저장**부터7일(7×24시간). 단순 페이지 열기·폰트 변경·조회·토큰 갱신은 만료 연장 사유가 아니다. 각 검사 만료는 독립적으로 검사한다.
- 완료 증명은 양쪽 회차/응답에 결합하고, 만료는 두 검사의 만료 중 빠른 시각을 넘지 않게 한다. 한 검사 만료/답변 변경/재검진 시 통합 증명과 대기 요청을 무효화한다. 다른 검사의 유효 응답은 보존한다.
- 시작/복원/이어하기/저장/전송/탭 재활성화/다른 탭의 storage 이벤트 때 만료를 확인한다. 활성 탭에는 남은 기간 타이머를 추가한다. 전송 전 재확인으로 만료 자료의 PDF 생성 차단.
- **브라우저가 닫힌 동안7일 정각의 물리 삭제를 보장하지 않는다.** 다음 실행 때 검사/제거한다. 브라우저 시계 조작/과거·미래 메타데이터는 신뢰할 수 없으므로 서버 처리에는 서버 서명 발급/만료 검증을 검토한다. 법적 고지에 절대적7일 원격 삭제를 약속하지 않는다.

### 이용자 직접 삭제

홈·전송 화면에 ‘검사 데이터 모두 삭제’ 진입점을 두는 안. 확인창에 두 검사 응답/진행/완료 증명·관련 동의 임시 기록이 지워지고 이어하기가 불가능함을 설명한다. 글자 크기는 선택적으로 유지한다. `localStorage.clear()`로 다른 사이트 기능/키까지 지우지 않는다.

삭제 시 해당 키 제거·React/폼 메모리 초기화·대기 요청 회차 무효화·다른 탭 통지. 진행 중 요청은 늦은 응답으로 자료를 되살릴 수 없게 한다. 이미 접수된 메일/GCS 표식/플랫폼 로그는 브라우저 삭제로 지워지지 않는다고 표시한다. 발송 중 삭제를 누른 경우 실제 전송 취소가 보장되지 않으며 결과 불명 상태에서 새 티켓을 자동 발급해 재발송하지 않는다. 메일 사본 삭제는 담당자 연락 경로를 안내한다.

공유기기에는 ‘응답이 이 브라우저에 남습니다. 다른 사람이 볼 수 있으니 종료 전 삭제하세요’를 검사 전·종료 화면에 표시하는 안. 로그아웃과 검사 삭제의 차이를 명시한다. 사용자 기기의 OS/브라우저 백업 복구까지 앱이 통제한다고 주장하지 않는다.

### 구버전 호환 선택

| 대안 | 장점 | 문제/선택 필요 |
| --- | --- | --- |
| 동의 후 명시적 이전 | 원 응답 유지, 기존 v1 엔진 재사용 | 기존 저장일을 알 수 없어7일 기산점은 **이전 승인 시점**으로 새로 기록한다고 고지. 과거7일 준수를 보장하지 않음 |
| 기존 자료 폐기 후 새 검사 | 정책과 회차가 명확함 | 응답 손실, 사용자 별도 승인 없이 적용하면 안 됨 |
| 자동 이전/자동 연장 | 클릭 부담 적음 | 불명확한 보관 기간·사전 동의 문제를 덮으므로 권장하지 않음 |

권장: 기존 자료 발견 시 개인정보 내용 자체를 표시하기 전 ‘이전하여 이어하기/삭제하고 새로 시작’ 선택. 동의 거부 시 서버에 전송하지 않고 삭제 경로를 제공한다. 실제 이전·삭제는 승인 전 하지 않는다.

향후 시험:7일 직전/정확한 경계/경과, 폰트·조회 미연장, 탭/새로고침/오프라인·시계 이상, 저장 실패, 구버전 선택, 한 검사 만료/독립 재검진, 삭제 후 늦은 응답, 전달 완료/불명 상태 유지, 이름/번호 미저장. 이 시험들은 **아직 구현/실행하지 않았다.**

## 5. 동의 문구 초안 및 법적 선택

[이전 A~E 초안](privacy-preproduction-review.md#동의-문구-초안--화면-미반영)의 빈칸을 유지하고 다음 시점을 분리한다. 검사 완료 확인 시각을 동의 시각으로 사용하지 않는다.

| 구분 | 제안 시점/필수 고지 | 짧은 문구 초안 |
| --- | --- | --- |
| 수집·이용 | 검사 전, 처리자/목적/항목/기간/거부 효과/문의처 | ‘[처리자]는 검사 저장·이어하기·완료 확인과 요청한 PDF 전송을 위해 필요한 정보를 처리합니다. 브라우저 응답은 [확정7일 기준]을 따르며 메일 사본은 별도 정책이 적용됩니다. 거부 시 해당 기능을 이용할 수 없습니다.’ |
| 민감정보 별도 | 첫 응답 저장 전, 건강 응답·각 집계/목적·기간 | ‘건강/생활 관련50문항 응답 및 집계를 위 검사·완료 확인·PDF 처리에 사용하는 데 별도로 동의합니다. 이는 의료 진단/체질 판정이 아닙니다.’ |
| 제3자 제공 | 독립 수신자로 확정 시 전송 전, 한의원명/목적/항목/받는 자 기간/거부 효과 | ‘[한의원]의 [상담 접수 목적]으로 이름·전화번호·완료 확인 시각·두 집계표 PDF를 제공합니다. 보유기간은 [확정값]이며 거부 시 이 경로의 전송이 제한됩니다.’ |
| 위탁/내부 접수 | 관계 확정 후 고지·계약 | 제3자 제공 체크박스를 무조건 쓰지 않고 위탁자/수탁자/재위탁·업무 범위/감독·파기와 권한 공개로 재구성 |
| 국외 이전 | 해당 법적 근거 선택 후, 제품별 국가/시기/방법/상대/연락처/목적/기간/거부 절차 | ‘[확인한 국가/상대]에 [항목]을 [방식/목적]으로 처리·보관합니다. [기간/거부 방법·효과].’ 빈칸 상태로 운영 사용 불가 |
| 거부/철회 | 각 목적별 별도 설명 | ‘거부할 수 있으며 [해당 검사 저장/전송]만 제한됩니다. 다른 진료·상담 전체의 제한을 의미하지 않습니다. [대체 문의처]로 문의하세요.’ |

법적 관계별 선택:

- **독립 앱→독립 한의원:** 제공 관계를 명확히 설명하기 좋으나 각 처리자의 고지·수신 보유기간·권리 대응이 필요. 법적 사업 주체, 제공 근거, 한의원 자기 목적을 확인한다.
- **한의원 위탁 앱:** 한의원 지시/책임과 기술 처리 범위를 정리할 수 있으나 위탁·재위탁 계약/공개·감독·삭제를 합의해야 한다. 개발자/Google/메일 서비스의 실제 계약을 확인한다.
- **한의원 직접 운영:** 내부 접수로 단순화될 수 있으나 동일 법적 주체인지, 외부 개발자의 권한·서비스 이용을 어떻게 처리하는지 확인해야 한다.

단지 이메일 도메인이 네이버라는 이유로 위 관계를 결정하지 않는다. 건강 문항/집계의 민감정보 해당성, 진료기록 편입, 미성년자 처리, 개인 Gmail의 실제 업무 적합성은 법률·한의원 책임자 검토 항목이다. [민감정보 제23조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0023&lsiSeq=283839&urlMode=lsScJoRltInfoR), [국외 이전 제28조의8](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334957); 수집·제공·위탁 근거는 이전 문서의 제15/17/26조 링크 참조.

### 동의 증빙 설계

`consentedAt`(동의 시각), `confirmedAt`(검사 완료 확인 시각), `submittedAt`(전송 시각)을 다른 사건으로 관리하는 안. 문구 버전/정적 전문 해시, 처리자/수신자/목적·정책 버전, 각 체크/거부, 회차와 계정의 최소 연결을 구분한다. 클라이언트 시각만으로 증거를 만들지 않고 동의 사건을 서버에서 확인하는 방안을 검토하되 이를 완료 확인과 혼동하지 않는다.

서버에는 원 응답·개인정보 DB를 새로 두지 않는 조건을 유지한다. 브라우저만 보관하면 삭제/기기 분실 후 입증할 수 없고, 현재 HMAC 표식은 문구/동의를 재구성할 수 없다. 후보는 한의원 관리 기록에 최소 서명 증명을 수신·보관하는 안(기존 메일/허용된 기록 시스템)과 별도 수동 동의 기록이다. 장점은 새 DB 없이 책임 소재를 정할 수 있음, 단점은 사본/권한/삭제 부담과 제출자 연결을 따로 설계해야 함이다. 최종 PDF 디자인은 변경하지 않으며 증명 전달 방법·기간·법적 근거는 승인 전 구현하지 않는다. 유료 저장소가 필요해지면 필요성·비용부터 별도 보고한다.

## 8. 사용자 결정/승인 대기

1. 사전 고지·일반/민감정보 별도 동의 후 검사 저장과 서버 완료 확인을 허용하는 A안으로 상세 UI 개발을 진행할지.
2. 검사별 마지막 저장7일, 증명 연동 만료, 직접 전체 삭제, 구버전은 동의 후 명시적 이전 또는 폐기 선택을 채택할지.
3. 법적 운영 주체/한의원 관계 및 정식 명칭·담당자·문의처·업무 수신 동의를 어떻게 확정할지.
4. 메일7일/접수30일/임시파일7일과 삭제 책임·동의 증빙/국외 이전 근거를 책임자/법률 검토에 회부할지.

이 네 가지 검토가 개인정보 기능 구현 승인, 정책 최종 승인, 운영 배포 승인을 자동으로 합치지 않는다. 이슈 #4는 정책·운영 준비 최종 승인까지 열린 상태를 유지한다.
