# E단계 사전 검토 — Gmail 발신, 테스트 네이버 수신

2026-10-26 검토. 이 문서는 계획이며 API 활성화, OAuth 인증, 실제 발송, 공유 저장소 생성은 실행하지 않았다. 사용자가 **개인 Gmail 발신 주소와 개인 네이버 1차 수신 주소를 제공**했다. 실제 주소는 이 저장소와 이슈에 기록하지 않는다. **한의원 공식 주소도 확보했지만 초기 시험에는 등록·사용하지 않으며, 적용은 1차 통과 후 별도 승인 대상**이다.

## 수신자 분리와 서비스 변경

| 구분 | 발신 | 수신 서버 설정 제안 | 상태 |
| --- | --- | --- | --- |
| Staging 1차 | 사용자 지정 개인 Gmail | `STAGING_RECIPIENT_EMAIL` = 사용자 지정 개인 네이버 | 주소 제공 완료, 설정/발송 별도 승인 |
| 한의원 수신 확인/운영 | 운영 전 별도로 확정 | `CLINIC_RECIPIENT_EMAIL` = 확보한 한의원 공식 주소 | 초기 시험에서 제외, 적용 별도 승인 |

이 이름들은 향후 설정 계약안이며 현재 환경에 등록하지 않았다. 프로젝트/환경에 맞는 값 하나만 읽고, 누락·잘못된 환경·미승인 주소·테스트 주소의 운영 재사용은 발송 전에 차단한다. 서로 다른 환경의 값을 대체값으로 사용하지 않는다. 브라우저는 to/cc/bcc/from/수신 모드 등을 보내지 못하며 추가 필드 요청은 지금처럼 거부한다. 클라이언트 빌드와 사용자 응답에 실제 수신 주소를 넣지 않는다.

발신 인터페이스와 PDF 생성은 유지하고 수신 메일 서비스와 독립시킨다. 네이버 전용 API나 네이버 비밀번호는 발송에 필요하지 않다. 한의원이 네이버·Gmail·자체 도메인 중 어느 것을 쓰더라도 서버 수신 설정 및 실제 전달 검증으로 대응한다. Gmail API 성공은 최종 수신함 도착을 증명하지 않으므로 서비스 변경 때마다 수신함/스팸함, 첨부파일·한글·파일명을 다시 확인한다. 운영으로 바꾸는 것은 단순 설정만으로 자동 승인되는 작업이 아니다.

## 사용자 승인 후 OAuth 절차

1. 테스트 Gmail 발신자와 네이버 수신자, 계정 소유자·접근 권한, 가상 데이터만 사용하는 발송 건수를 확정한다.
2. 테스트 프로젝트에만 Gmail API를 활성화하고 Google Auth Platform의 앱 정보·담당 연락처·External/Testing 사용자 목록을 구성한다. 개인 Gmail에는 Workspace 내부 앱 방식을 쓰지 않는다. 발신 계정 A를 OAuth 테스트 사용자로 등록한다. 네이버 수신자는 Google OAuth를 승인하지 않는다.
3. 신뢰할 수 있는 로컬 관리자용 일회성 OAuth 도구와 정확한 redirect URI를 구성한다. authorization-code flow, state/PKCE 검증, 짧은 처리 시간, 승인 코드 미기록을 적용한다. 환자 화면에 관리자 인증 콜백을 노출하지 않는다.
4. **발신 계정 소유자**가 Google 화면에서 자신의 계정을 확인하고 `https://www.googleapis.com/auth/gmail.send`만 직접 승인한다. 메일 읽기·수정·삭제 권한이나 수신 계정 권한은 요청하지 않는다. 현재 Firebase CLI 로그인은 이 승인을 대신하지 않는다.
5. offline access로 받은 refresh token과 OAuth client secret은 테스트 Secret Manager에만 보관한다. access token은 서버 메모리에서 갱신한다. 키/토큰을 GitHub·브라우저 저장소·이슈·로그·명령줄 인자에 넣지 않는다.
6. 서버의 명시적 허용과 고정 테스트 수신자·공유 중복 상태를 확인한 뒤 가상 PDF를 소수 건만 보낸다. MIME 제목/본문은 개인정보를 제외하고 파일명 UTF-8 인코딩을 확인한다. 네이버 소유자가 실제 도착·스팸함·첨부를 확인한다. 읽기 확인을 위해 Gmail 읽기 권한을 추가하지 않는다.
7. 토큰 철회·만료·네트워크 장애·전송 결과 불명·중복 요청·운영/테스트 수신 혼선을 검증한다. 테스트 종료 시 발송을 다시 비활성화하고 필요 시 OAuth 철회/Secret 비활성화한다.

공식 [서버 OAuth 흐름](https://developers.google.com/identity/protocols/oauth2/web-server), [환경 분리와 OAuth 정책](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance)을 기준으로 세부 도구와 권한을 승인 전에 제시한다. 현재 배포 보호는 `MAIL_MODE=mock`, `SEND_ENABLED=false`만 허용하므로 E단계에는 별도 코드·보호 규칙 검토가 필요하다.

## 검증 필요 여부와 토큰 수명

`gmail.send`는 [민감한 권한](https://developers.google.com/workspace/gmail/api/auth/scopes)이다. Google 공식 안내에서 Development/Testing/Staging 앱은 테스트 사용자와 경고/사용자 수 제한 아래 검증 없이 시험할 수 있다. 따라서 이번 제한된 E 시험과 불특정 사용자용 운영 검증 요건을 구분한다. 실제 한의원 운영 서비스가 개인 사용 예외에 해당한다고 단정하지 않는다. 공개 운영 전에 앱 형태에 맞춰 검증/브랜딩·도메인·정책 문서·권한 시연 요건을 확인한다. [검증 및 예외 안내](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)

External Testing에서 Gmail 권한을 포함해 받은 refresh token은 일반적으로 **7일** 만료된다. access token은 응답의 `expires_in`에 따라 갱신하고, refresh의 `invalid_grant`·철회·비밀번호/계정 상태 변화 등은 발송 중지와 계정 소유자 재승인으로 처리한다. 인증 실패에 무제한 재시도하지 않는다. Production 게시가 영구 토큰을 보장하지 않으며 운영 전에 별도 검토한다. [Google 토큰 만료 안내](https://developers.google.com/identity/protocols/oauth2#expiration)

## 저비용 공유 상태 비교 — 생성 안 함

| 대안 | 비용/구조 | 원자성·장애 제약 | 판단 |
| --- | --- | --- | --- |
| 현재 프로세스 메모리 | 추가 저장소 비용 없음 | 재시작·리비전 변경 시 소실, 전역 제한 불가 | 모의 테스트 한정 |
| 별도 비공개 Cloud Storage Standard 버킷 | 객체 바이트·작업 수·네트워크 종량제, 상시 컴퓨팅 불필요 | 생성 전제조건/세대 번호로 예약·갱신 가능. 공유 카운터 경합·만료 정리·결과 불명 처리 필요 | 소규모 E 후보 우선 검토 |
| Redis 계열 | 인스턴스/네트워크 등 상시 비용 가능 | TTL·원자 연산에 유리하나 장애·영속성 정책 필요 | 별도 승인 없이 생성하지 않음 |
| Firestore | 이번 프로젝트에서 사용 금지 | 비교의 운영 후보로 채택하지 않음 | 생성하지 않음 |

GCS안은 `ifGenerationMatch=0` 원자 예약, 세대 조건부 상태 갱신, 승인한 논리 만료 기간을 이용한다. 객체에는 불투명 요청 키·HMAC·상태·시각·시도 횟수 및 필요한 비개인 집계만 제안한다. 이름·전화번호·응답·점수·PDF·수신자 주소는 저장하지 않는다. HMAC/운영 메타데이터가 무조건 익명정보인 것은 아니다. 스코프별 키와 최소 권한도 승인 항목이다. [원자적 조건부 요청](https://docs.cloud.google.com/storage/docs/request-preconditions)

기존 Functions 배포 버킷을 처리 표식 저장에 재사용하지 않는다. D점검에서 배포 버킷의 soft delete 7일을 확인했다. 새 후보 버킷은 public access prevention·uniform access·버전 보관·soft delete·retention 설정을 별도로 승인해야 한다. 논리 TTL과 실제 삭제를 구분하며 lifecycle 비동기 정리만으로 24시간 물리 삭제를 보장하지 않는다. soft delete를 유지하면 삭제 후 보관과 비용이 생긴다. [수명주기](https://docs.cloud.google.com/storage/docs/lifecycle), [soft delete](https://docs.cloud.google.com/storage/docs/soft-delete)

## 중복·요청 제한과 결과 불명

권한/App Check·본문 제한·입력 검증·버튼 잠금은 유지하고, 공유 예약/상태 갱신과 일일 한도는 저장소 승인 후 구현한다. 초기 실제 시험 한도는 전체 하루 10건을 제안하며 최종 수치는 사용자 승인 후 확정한다. 카운터 확인 실패나 수신자/토큰 설정 누락 시 발송하지 않는다.

| 결과 | 처리 계획 |
| --- | --- |
| 입력/동의 오류 | 수정 가능, 미발송 |
| 발송 전 명확한 실패 | 같은 요청 키로 제한적 재시도 |
| Gmail 성공 응답 기록 완료 | 동일 요청 재발송 차단, 수신 확인은 별도 |
| Gmail 호출 도중 timeout/응답 유실, 성공 후 상태 기록 실패 | 결과 불명으로 잠금, 자동 재발송 금지, 발신/수신 계정 소유자가 확인 |

저장소와 Gmail을 하나의 트랜잭션으로 묶지 못하므로 정확히 한 번 발송을 보장하지 않는다. 예약 TTL 만료가 결과 불명 요청의 재발송 허가가 되어서는 안 된다. 현재의 모의 실패 재시도 정책을 실제 Gmail에 그대로 사용하지 않는다. [Gmail send API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send)

## 보관·삭제와 개인정보 책임

E는 지정 가상 정보만 사용한다. 실제 환자 자료는 처리방침/동의·한의원 책임 관계와 운영 승인 전에는 금지다. 첨부파일명에도 이름과 전화번호 일부가 들어가므로 관련 고지를 유지한다.

- 서버: 인적사항·응답·PDF는 메모리 처리만 유지. 요청/예외 본문 로깅 금지. 실행 플랫폼의 IP·시각·상태 로그가 남는 것은 별도 고지/권한·기간 검토 대상이다.
- 발신 Gmail과 수신 네이버: 보낸편지함·받은편지함·스팸함·휴지통·다운로드 사본을 각각 계정 소유자가 확인/삭제해야 한다. `gmail.send`로 보관 메일의 자동 삭제를 보장하지 않으며 삭제를 위해 권한을 확대하지 않는다.
- 제안: 가상 테스트 메일과 다운로드 사본은 검증 후 수동 삭제하고 최대 7일 내 휴지통까지 정리하는 책임자를 양쪽에 지정한다. 공급자 백업의 물리 삭제까지 이 절차로 보장하지 않는다. 실제 운영 보관 기간은 미정이며 한의원 승인 필요다.
- 공유 메타데이터: 논리 유효기간(예: 24시간), 실제 정리 지연/복구 보관/장애 시 보존의 의미를 별도 확정한다.
- 운영: 개인정보처리자/위탁/제3자 제공, 민감정보, 국외 이전·해외 서비스 처리, 동의 증빙, 계정 접근자·보관·파기 책임을 전문가와 한의원이 검토해야 한다. 임시 체크박스만으로 법적 요건 충족을 확정하지 않는다.

## 비용과 승인 체크

추가 가능 비용은 소수 이메일 API 호출 자체보다 Functions 실행·빌드·아티팩트·Secret 버전/접근·GCS 작업/저장/네트워크·CAPTCHA가 중요하다. 정확한 원화 견적은 승인할 리전·요청량·보관·결제 계정 무료 할당을 반영해야 한다. 상시 Redis는 소규모 시험에서 고정비가 커질 수 있어 우선안으로 선택하지 않는다. [Storage 가격](https://cloud.google.com/storage/pricing), [Secret Manager 가격](https://cloud.google.com/secret-manager/pricing), [Firebase 가격](https://firebase.google.com/pricing)

현재 월 KRW 10,000 알림(50/90/100%)은 유지하되 과금 상한으로 보지 않는다. 실제 누적 청구액은 비용 보고서에서 별도로 확인해야 하며 예산 설정만으로 0원을 주장하지 않는다.

E 실행 전에 필요한 승인:

1. 실제 테스트 Gmail 발신 주소/소유자와 네이버 수신 주소/소유자, 소수 시험 발송 허용.
2. Gmail API 활성화·OAuth 앱/클라이언트 구성·소유자 직접 권한 승인·Secret 추가.
3. 공유 저장소 선택, 메타데이터 항목, 정리/soft delete/장애 정책, 월 비용 범위와 시험 한도.
4. 빌드와 실행 계정 분리 및 최소 권한 변경. 현재 기본 계정은 빌드 역할을 공유하므로 실제 개인정보 도입 전 개선 필요. 키 파일은 만들지 않는다.
5. 가상 메일/다운로드 삭제 담당자·기간 및 결과 불명 수동 확인 절차.

한의원 수신 주소가 정해지더라도 운영 변경은 F/G 최종 승인 대상이다. 이번 D작업에서는 위 설정·인증·발송·새 저장소를 실행하지 않았다.

## E 실행안 — 검토 가능한 승인 범위

아래는 실행 전 승인할 구체안이다. 아직 생성·구현·배포하지 않았다.

- 대상은 `yingyangtest`와 `develop/v1.2`만. 운영·main·출시 태그는 유지.
- 초기 수신자는 제공받은 네이버 한 주소에 고정. 한의원 주소는 미등록 상태로 두고 다른 주소로의 fallback 금지. 네이버 1차 시험 통과 보고 후 한의원 수신 확인을 별도 승인받는다. 한의원 확인도 곧바로 운영 프로젝트 변경을 허용하는 것은 아니다.
- Gmail API 활성화, External/Testing OAuth 구성과 발신 소유자의 `gmail.send` 직접 동의. 비밀 등록은 Secret Manager 최대 2개 추가를 제안하며 비밀을 채팅/이슈/저장소에 받지 않는다. OAuth 클라이언트 생성 등 콘솔에서 소유자가 직접 해야 하는 단계는 안내한다.
- 별도 비공개 GCS Standard 버킷 1개, 서울 리전, uniform access/public access prevention, 버전 관리 끔, soft delete 끔을 제안. 보관할 것은 불투명 요청 키/HMAC/상태/시각/시도 및 일일 카운터뿐이고 인적사항·응답·PDF·이메일 원문은 금지.
- 표식 논리 유효기간 24시간과 비동기 lifecycle 정리를 구분. 정확한 24시간 물리 삭제는 보장하지 않는다. 결과 불명 상태는 자동 재발송하지 않는다. 기존 배포 버킷은 재사용하지 않는다.
- 키 파일 없는 Staging 실행 서비스 계정 1개를 만들어 빌드 계정과 분리하는 안. 해당 버킷의 필요한 객체 권한, 해당 비밀의 접근 권한 및 필요한 로깅 권한으로 제한한다. 서비스 계정 생성 자체도 이번 승인 항목이며 기존 지침에 따라 승인 전에 만들지 않는다.
- 승인된 네이버 대상으로 전체 하루 최대 10건, 기본 발송 끔, 명시적 시험 허용 때만 켬. 토큰/수신 설정/공유 상태 확인 실패 시 발송 차단.
- 가상 메일·다운로드는 검증 후 수동 삭제, 최대 7일 내 양쪽 휴지통까지 정리하는 안. 담당자는 사용자 또는 지정한 계정 소유자.
- 비용은 기존 Functions/Secret 및 소량 GCS 종량제다. 무료 할당 공유·리전·작업량에 따라 달라져 현재 확정 원화 견적은 제시하지 않는다. 기존 월 1만원 예산 알림을 유지하며 비용을 강제로 차단하는 것으로 표현하지 않는다. 상시 Redis·Firestore·Scheduler 등 다른 서비스는 승인 범위에 넣지 않는다.

허용 범위는 ‘OAuth 설정 준비만’ 또는 위 구체안의 ‘가상 데이터 E 시험 전체’로 구분해 확인한다. 준비만 승인되면 실제 OAuth 권한 승인·발송·GCS/서비스 계정 생성은 계속 보류한다. 사용자에게 별도 승인을 유지하라는 지시가 있었으므로 주소 제공만으로 이 실행 승인을 대체하지 않는다.
