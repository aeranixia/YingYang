### 별도 마스터 로그인·비밀번호

- 별도 ID 로그인은 마스터만 사용한다. 최초 일회용 로그인은 기존 Staging 설정 담당자 인증 후에만 허용하고 즉시 비밀번호 변경을 강제한다. 강제 변경 전 로그·PDF·계정 관리 모두 서버에서 차단한다.
- 비밀번호는 무작위 salt와 scrypt 해시만 비공개 저장소에 보관한다. 현재 비밀번호 확인 후 새 Firebase 인증 토큰을 발급받아 5분 안에 12자 이상 새 비밀번호로 변경한다. 변경하면 버전을 증가시키고 refresh token을 취소하여 이전 토큰을 차단한다.
- 잘못된 비밀번호 5회는 15분 잠금한다. 로그인 성공 시 실패 횟수는 초기화한다. 조건부 GCS 쓰기로 동시 변경 충돌은 차단한다. 인증 API는 프로세스당 분당 30회, 이력 API는 분당 5회 제한이다. 전역 DDoS 방어를 보장하지 않는다.
- 계정 승인·회수·초기화는 최근 5분 내 본인 확인이 필요하다. Google 계정의 본인 확인은 Google 재인증으로 수행하며 앱에서 Google 비밀번호를 변경하지 않는다. 별도 마스터 초기화는 고정 Google 웹마스터만 할 수 있고 일회용 로그인 후 다시 변경해야 한다.
- 일반 관리자 권한 회수는 매 요청마다 확인하므로 기존 ID 토큰에도 즉시 적용된다. 연결된 Firebase refresh token도 취소한다. 초기화는 별도 마스터에만 적용하고 일반 Google 계정 비밀번호 초기화 기능은 제공하지 않는다.

### 관리자 계정 저장소·권한

별도 Staging 비공개 서울 STANDARD 버킷 `yingyangtest-admin-identity-495270334718`에 고정 웹마스터 설정, 별도 마스터 해시, 승인 Gmail·연결 UID·상태를 보관한다. 환자 응답·PDF는 이 버킷에 넣지 않는다. 관리자 계정 설정은 서비스 이용 기간 동안 유지하고 권한 회수 이력은 inactive 상태로 보관하므로 자동 7일 삭제 대상이 아니다. 관리자 개인정보의 보관 종료·계정 폐기 정책은 운영 전 확정해야 한다.

버킷은 공개 접근 금지, 균일 권한, 버전 관리·soft delete 비활성화이다. 인증 감사의 `audit/` 객체만 lifecycle 7일 삭제하며 작업 종류·시각·HMAC 처리한 행위자/대상 식별값을 기록한다. 비밀번호·토큰·해시는 로그에 기록하지 않는다. GCS lifecycle은 비동기 삭제이다. 기존 PDF 버킷의 7일 보관은 그대로 유지한다.

기존 실행 계정에 이 버킷의 objectAdmin, 프로젝트의 사용자 조회·토큰 취소용 `firebaseauth.users.get/update`, 자기 자신에 대한 `iam.serviceAccounts.signBlob`만 추가한다. 서비스 계정 키는 만들지 않는다. IAM Credentials API와 기존 GCS 소량 저장·요청의 종량제 비용이 발생할 수 있고 고정 인스턴스는 추가하지 않는다.

### 공개 가입 제한과 관리자 사전 등록

Google 제공자 활성화 후 실제 첫 로그인에서 `auth/admin-restricted-operation`이 발생했다. 기존 `disabledUserSignup=true`가 확인됐으며 공개 가입 제한을 그대로 유지한다. [Identity Platform 사용자 제한 설명](https://docs.cloud.google.com/identity-platform/docs/concepts-manage-users)을 참고한다.

사용자가 웹마스터·승인 관리자 사전 등록과 기존 Staging 실행 계정의 `firebaseauth.users.create` 추가를 명시 승인했다. 고정 웹마스터는 사전 등록 후 사용자가 실제 Google 로그인·마스터 화면을 확인했고 서버에서도 고정 이메일 일치·검증·Google 연결·활성 상태 및 UID 고정을 확인했다.

일반 관리자 승인 시 서버가 Firebase Auth 계정을 먼저 조회하고, 없는 경우에만 비밀번호 없이 생성한 뒤 해당 UID를 승인 기록에 연결한다. 이메일 인증을 서버에서 임의 완료 처리하지 않는다. 기존 계정의 자격증명·인증 상태를 변경하지 않으며 비활성 계정은 거부한다. 동시 생성 충돌은 기존 계정 재조회로 처리한다. 생성 후 승인 기록 쓰기가 실패하면 Auth 계정이 남을 수 있지만 서버 승인이 없어 관리자 자료에는 접근하지 못한다. 관리자가 정리해야 한다.

사용자 생성 권한은 기술적으로 프로젝트 범위이므로 서버에서 마스터·최근 본인 확인·승인 Gmail 검사를 강제한다. 새 서비스 계정이나 키는 생성하지 않았다. 권한 회수는 관리자 승인 상태를 비활성화하고 refresh token을 취소하며 Firebase Auth 사용자 자체를 삭제하거나 Google 계정을 변경하지 않는다. 팝업 닫힘은 별도 안내하고 기존 승인 세션을 유지한다.

관리자 Firebase Auth에는 이메일·UID·제공자 연결·로그인 메타데이터와 Google 로그인에서 제공하는 프로필이 남을 수 있다. 환자 검사 자료와 구분하며 관리자 계정 폐기 시 Auth 사용자 및 승인 기록의 정리 책임·보관 기간을 운영 전에 확정해야 한다.

## 실패·중복 보존

PDF 보관 실패는 발송 전에 실패 처리한다. 실제 Gmail이 접수된 뒤 이력 상태 갱신만 실패한 경우, 기존 공유 발송 성공/불명 표식을 유지하며 자동 재발송하지 않는다. 이력에는 대기가 남을 수 있어 UI에서 대기를 ‘진행 중 또는 최종 상태 미확인’으로 설명한다. 관리자 다운로드는 상태에 관계없이 권한·보관기간을 확인하므로 파일을 확인할 수 있다. 이력과 Gmail 전달을 하나의 원자적 트랜잭션으로 보장하지 않는다.

공유 메일 중복 방지·KST50회 시도 제한·결과 불명 자동 재시도 금지는 유지한다. 모의 처리의 기존 프로세스 메모리 중복 제한을 영구 전역 보장으로 바꾸었다고 주장하지 않는다.

## 안내·개발 경계

PDF에 전체 이름·번호·집계가 들어 있는7일 비공개 보관 사실과 관리자 접근 기록을 정책·검사 전/후 안내에 추가했다. 변경된 범위에 재동의를 받도록 버전을 갱신했으며 기존 응답·저장일/키는 유지한다. #4의 운영 법적 검토를 완료하거나 운영 배포를 재개하는 변경은 아니다. 가상 정보만 사용한다.

롤백은 개발 브랜치의 직전 커밋3a093ad와 기록된 이전 Hosting/Functions 리비전을 기준으로 한다. 기능 플래그 STAGING_ADMIN_ARCHIVE_ENABLED를 끄면 새 PDF 보관/관리자 API를 차단할 수 있지만 기존 비공개 보관분은 만료 정책으로 정리해야 한다. 이미 내려받은 사본은 회수되지 않는다. 새 버킷을 보존 정책 확인 없이 삭제하거나 운영에 복사하지 않는다.

## 검증 결과

최종 실행과 검증 한계는 docs/verification.md 및 #7 통합 보고에 기록한다. 물리적7일 경과 자동 삭제를 실제로 기다린 검증과 논리 시각을 이용한 만료 시험을 구분한다. 운영·실제 Gmail 시험은 하지 않는다.

최종 검증(2026-11-01): UI60+보호2+서버44=106개 통과, 일반/Staging/Functions 빌드 성공. Hosting/Functions 기존4개 업데이트·관리자2개 생성 및 release 완료 확인. PowerShell 파이프 종료코드1은 배포 실패로 단정하지 않고 실제 HTML/JS HTTP200·로컬 빌드 해시 일치로 추가 확인했다.
