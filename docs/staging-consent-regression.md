# Staging 동의 후 검사 진입 회귀 수정 — 2026-11-01 KST

승인: 이슈 #4 댓글6545093823. 사용자는 동의 체크2개 후 시작/이어하기 버튼에서 넘어가지 않는다고 확인했다.

## 확인된 경로

실제 배포 stagingStatus는 ACTIVE이며 배포 소스의 package main은 lib/functions/src/index.js, 사용 중 privacy.js 버전은 staging-clinic-privacy-2임을 다운로드 소스로 대조했다. Hosting JS도 해당 버전이다. 예전 lib/index.js가 소스 묶음에 존재하지만 package main은 이를 가리키지 않는다. 버전 불일치나 잘못된 엔트리로 단정하지 않았다.

WebKit 자동화의 격리된 테스트 계정 흐름에서 환경 확인200·BC, 동의 발급200·proof 반환 후 동의 화면을 통과하지 못하는 현상을 재현했다. 추가 진단에서 서버 발급 시각이 브라우저보다11ms 앞선 값을 관측했다. 기존 acceptPrivacy와 privacy는 at이 브라우저 Date.now보다 조금이라도 앞서면 각각 저장 거부/동의 무효로 처리했다. 같은 경로는 서버 시각을1초 앞당긴 회귀 테스트로 검증했다. 사용자 브라우저의 개별 응답은 확보하지 않았으므로 사용자 장애 원인을 유일하게 확정했다고 주장하지 않는다. 추가 진단 스크립트 한 번은 실패 처리 코드의 범위 오류로 상세 결과를 남기지 못했으며 앱 오류로 집계하지 않는다.

## 수정 범위

- 브라우저 동의 발급 시각 검사에 최대60초 시계 차이 허용. 서버 서명·버전·Auth/App Check·서버 만료 검증은 변경하지 않는다. 원래 expires를 연장하지 않으며60초를 넘는 미래 시각은 거부한다. 브라우저 시계를 크게 틀리게 설정한 경우 여전히 진입하지 못할 수 있다.
- 동의 처리 중 일반 interval 점검을 건너뛰고, 이전 비동기 verify 결과가 새로운 동의 상태를 덮지 않도록 세대 검사를 추가했다. 다른 탭 삭제/epoch 검사는 유지한다.
- 중복 클릭을 ref로 잠그고 실패 시 finally에서 busy/checking을 복구한다. 실패 단계와 허용된 Firebase 오류 코드만 표시하며 원본 메시지·토큰·응답을 노출하지 않는다. 새 개인정보 로그는 추가하지 않는다.
- 응답·저장 키·7일 보유기간·문항·PDF·집계·동의 문구·메일 기능 변경 없음. 완료 시각을 새로 생성하거나 조작하지 않는다.

## 검증과 배포

UI53 + 배포 보호2 + 서버36 =91개 통과. npm test, npm run build, npm run build:staging 성공. 회귀3개는 작은 시계 차이/큰 차이 거부 및 만료 유지, 동의 후 카드·첫 문항 이동, callable 거부 시 안전한 코드 표시·체크 유지·재시도를 확인한다.

승인된 yingyangtest Hosting만 배포했다. CLI에는 release complete/Deploy complete가 표시됐으나 PowerShell 파이프 실행의 종료 코드는1이었다. 이에 배포 완료를 메시지로만 판단하지 않고 실제 HTTP200 및 내려받은 JS와 로컬 빌드 해시 일치를 확인했다. Functions는 수정/재배포하지 않았다.

수정 후 단일 WebKit 자동화 흐름: 환경 확인200, 동의200(서버13ms 앞섬), 검진 카드 → 후천적 문항1/10 표시 성공. 실제 App Check·테스트 Auth를 사용했으며 가상 빈 검사 상태에서 첫 문항까지만 확인했다. 일반 Chrome/Edge·실제 Safari/모바일 검증으로 표시하지 않는다. 기존 Chrome 자동화403과 이번 서버200 이후 로컬 거부는 별개다. 검진 전체/PDF/이메일 반복 시험은 하지 않았다.

Staging HTTP200/배포 JS 일치, noindex·no-store 유지. 운영 HTML HTTP200·이전 기준 해시 일치. 실제 메일·발송 창·운영 배포·main·출시 태그·유료 자원 변경 없음.
